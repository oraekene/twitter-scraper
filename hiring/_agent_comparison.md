Here is the exact step-by-step backend process that agents like Claude Code or Cursor use when you say "go to Twitter and find opportunities." A standard agent consists of one model plus a harness. The model is the decision maker and the harness is everything around it: the system prompt, the tools the model can call, and middleware that shapes the loop. The loop is simple and repeated: the model receives the task, decides which tool to call, the tool runs and returns results, those results are appended to the conversation history, the model sees them, and it decides again until the task is complete. Tools are the model's only access to the outside world, and they are normal Python functions or LangChain tool wrappers with a name, a description, and an input schema. The execution environment is the agent's workspace: tools, a filesystem for reading and writing, and code execution for running scripts. Context management is needed because every model call has a fixed context window that fills with history and tool results, so summarization compresses old turns, memory persists instructions, and skills surface domain knowledge. Planning and delegation let a long task be broken into a todo list handed to subagents that each run in their own isolated context. Fault tolerance is handled by middleware through retries, fallbacks, and call limits. Guardrails add things like PII detection and human approval gates before high-impact actions. So the real backend flow for your request is: load the prompt plus a search tool and a fetch tool; call the official X API full-archive search with your query; parse the returned tweets; follow each t.co link with a fetch tool to the final page; read page text; and finally format the results. The whole thing is a loop driven by one model with a handful of tools, a short context, and a couple of middleware layers.

Now the red team of your system. Your pipeline has four separate discovery paths that overlap. roundup.py finds dated multi-item roundups with a regex that requires three or more list items and dates, seeded by two hardcoded tweet IDs and by a live X search that itself re-runs the same roundup rule on X's own results. opportunities_manual.json is a hand-maintained list of single programs that is seeded from hardcoded Python arrays and edited by people. roundup.find_single_tweets produces single-program tweets using a second regex gate that requires an apply phrase, an opportunity word, and a stated date. research.py is a third gate that classifies every tweet with an LLM and can also extract verified facts from pages. All four read the same 99,355-row bookmarks database, and they all converge on the same two output tables plus the same manual JSON file. That is redundant coverage: you run the roundup regex, the live X query, the single-tweet regex, and the LLM classifier on overlapping data to find the same thing.

There is also a second kind of duplication inside the report itself. DATED comes from hand rows, UNDATED comes from hand rows, parsed_roundups comes from regex-parse roundups, and _auto_undated comes from roundups without a date, but all four are merged into one table and deduplicated against each other at render time. So the output is one union of four overlapping inputs rather than one canonical source. And you have two registries doing overlapping work: the dedupe registry in dedupe.py remembers every program ever seen to flag it as previously seen, while research.py's own research.db carries its own scans and pages tables as a classification cache. Those two caches have different schemas, different keying, and different semantics, so a program found by both will show up twice until the merge layer dedupes it.

Despite that redundancy, your pipeline is not simply over-engineered, and here is the counter-argument. A naive agent run cannot do what your system does at scale because it has no memory across runs and no way to guarantee recall over tens of thousands of tweets. Your system reads the entire local DB once, caches every classification so the marginal cost of each later run is near zero, and keeps the hand list as the ordered human-in-the-loop authority. The human-curated manual list is not duplication for its own sake, it is the part that guarantees the important programs like Y Combinator and Thiel Fellowship are never missed by a missed keyword. A pure LLM classifier over 99k tweets with free routes that 429 after a handful of calls is exactly the failure mode you want to avoid, and your provider rotation plus per-provider cooldowns are a reasonable engineering response to that. The research module's separation of scan, enrich, and merge is also the right shape because the network I/O and the LLM calls are the slow paths and they need to be resumable independently.

The one place I would cut is the single-program regex path. roundup.find_single_tweets returns tweets with an empty program field and forces a human to name the program, but research.py already does this job better with semantic judgment and can be asked to output the program name directly, so the regex candidate generator plus the manual entry step becomes a single LLM step. The live X search overlap is also redundant if the LLM scan runs over the full DB: a live X query only re-searches the last 30 days, which is a subset of what the DB scan covers. Removing those two halves would remove one source of duplicated rows and one source of missed recall without removing the recall guarantee, because the manual list still anchors it.

The practical risk is not redundancy, it is throughput on free LLM routes. tokenharbor v4.1 answers in about two seconds and then 429s, literouter's qwen route works, and v4 takes about seven seconds. A full 99k classification at roughly two calls per 30 tweets plus enrichment fetches could take many hours on free quotas. So the scan may be running but not finishing this session, and enrichment will not produce new manual rows until the scan completes.
